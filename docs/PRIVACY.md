# Privacy and research activation limits

The public lesson stores its chapter, visited chapters and density in localStorage. Unsent assessment answers, written responses and F3/F5 questionnaire drafts use tab-scoped sessionStorage and are removed after successful submission. This is browser recovery, not database autosave; closing the tab can lose unsent work. Practice answers go to a scoring operation that does not persist them. No analytics SDK or research telemetry runs in the public demo.

The `/dev/study` development-only fixture uses a separate SYNTHETIC localStorage namespace for one simulated session and never sends research API requests. Reset clears the fixture; a fresh synthetic ID isolates any remaining tab draft keys. Do not enter identifying data into development tools. Production returns 404 for this route.

Consented E1 study mode uses an HttpOnly signed cookie and opaque server session. Return secrets contain 32 random bytes; only their SHA-256 hashes persist. The browser places return tokens in URL fragments, strips the fragment before recovery and sends no referrers. From migration 007 onward, approved enrollment asks for name and ERP; these are stored in a private identity table, separate from F0 and de-identified exports. Do not collect emails, exact birthdates, raw IP addresses, pointer trails or user-agent fingerprints.

The five-course recorded flow has a separate, closed-by-default gate. After approved identity/consent wording, it stores name and ERP in `course_student_identity`, while `course_attempts` stores course, server-assigned density, answers, score and timestamps. The current browser holds an opaque HttpOnly attempt token; only its hash is stored. The researcher Student records tab requires allowlist and TOTP MFA, and each view is audited. No name/ERP export is provided. Withdrawal excludes an attempt from that view and invalidates its cookie; physical erasure, retention and backup treatment require an approved policy. ERP is self-reported and not proof of identity, so duplicates/impersonation must be addressed in the protocol before recruitment.

Study events are allowlisted, bounded and deduplicated per session. The browser caps its retry queue at 200 events in per-participant sessionStorage, sends at five-second intervals and attempts a flush on visibility/page exit. Abrupt termination can lose unsent events. Background transmission is best-effort; no inference of inattention from missing events is permitted. Active-time reconstruction needs further validation.

Withdrawal marks the participant, closes the session and follow-ups, revokes return tokens and excludes records from exports. Physical deletion and backup expiry depend on the approved consent/retention policy and remain unresolved. No invented retention period or institutional contact is shown.

Administrator authentication uses Supabase-verified accounts, a server UUID allowlist and mandatory TOTP MFA (aal2) in production. Session cookies are HttpOnly, SameSite=Strict and expire with the token (at most one hour); sign-out revokes the Supabase session. This was verified against a local Supabase Auth server, not yet a hosted project, and still needs institutional review before sensitive use. Blind raters are recorded as pseudonymous codes, never account identities. Backend database credentials never go to browsers. Access logs at the deployment provider are separate infrastructure and need operational retention configuration.


M4 provides physical deletion behind PHYSICAL_DELETION_ENABLED=false. No retention period is assumed and no hosted deletion has occurred. An operator first runs the dry-run script. Applying one request requires an explicit participant UUID/policy version, a matching approved database policy, an elapsed configured delay and withdrawal. One transaction removes answers, written responses, ratings/adjudications, surveys, follow-ups, return tokens, events, participant limiter buckets, sessions, assignments and participant metadata. Private aggregate allocation counts remain without per-person identifiers, preserving balance; their retention is part of the review decision. Failed/concurrent requests cannot partly delete or double-count. Backups and provider access logs remain outside this mechanism and need approved expiry/restoration procedures; restoring a backup requires reapplying approved deletion requests under a separately retained institutional process.

Optional D/F6 uses the same private session/return-link protections and tab drafts. Its frozen review/window fields are absent on legacy sessions. The draft debrief is visible only through the development route, which is 404 in production. Response-based review summarizes allowed questionnaire answers by frozen cohort/form/version; no individual diagnosis, free-text analysis or automatic exclusion/adaptation occurs. Synthetic browser previews send no research requests.
